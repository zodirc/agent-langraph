# RAG 与 Skills 流程说明

## 1. 文档目标

这份文档专门说明当前项目中的两条核心流程：

- RAG 流程
- Skills 流程

文档只描述当前项目中的实际架构与执行方式，不讨论问题、不提出假设、不贴实现文件路径，也不贴代码路径。

目标是从系统流程角度，把这两个能力说明清楚。

---

## 2. 整体关系

在当前项目中，RAG 与 Skills 并不是两套彼此孤立的系统，而是统一运行时中的两个重要部分：

- **RAG** 负责为任务提供知识与证据支撑
- **Skills** 负责为任务提供场景策略、行为约束与能力边界

它们都服务于统一 Agent Runtime，但职责不同。

### 2.1 两者在系统中的位置

- RAG 更接近“知识补给与证据组织”
- Skills 更接近“场景约束与策略驱动”

二者都会影响规划、工具选择、上下文组织和最终输出结果。

### 2.2 两者协同关系

- Skills 决定系统在某个场景下如何做事
- RAG 决定系统在需要知识支撑时拿什么材料做事

所以它们的关系不是替代，而是协同。

## 3. RAG 流程总览

RAG 在当前项目中的目标，是为规划、推理、工程判断与结果生成提供知识支撑与证据材料。

它不是整个系统的总代称，而是统一运行时中的一个关键子流程。

## 4. RAG 流程详细说明

## 4.1 检索触发

RAG 流程并不是每次输入都强制执行，而是由前面的规划阶段决定是否需要知识支持。

也就是说，系统会先判断：

- 当前任务是否依赖外部知识
- 当前任务是否需要事实性支撑
- 当前任务是否需要背景材料
- 当前任务是否需要补足历史记忆之外的信息

当系统判断需要知识支撑时，才会进入检索链路。

---

## 4.2 检索意图与查询整理

在进入真正的召回之前，系统会先把当前任务转换为更适合检索的查询形式。

这一步的目标是让系统不要直接拿原始用户话术去搜，而是先整理出：

- 当前检索的目的
- 更适合检索的查询文本
- 必要的检索限制条件
- 与当前任务相关的上下文信息

这一阶段的输出，是后续召回所依赖的检索输入对象。

### 4.2.1 查询整理视图

```text
+------------------------+
| 原始用户目标            |
+------------+-----------+
             |
             v
+------------------------+
| 任务语义抽取            |
| - 主题                  |
| - 约束                  |
| - 目标类型              |
+------------+-----------+
             |
             v
+------------------------+
| 检索目的判断            |
| - 事实核对              |
| - 规范参考              |
| - 背景补足              |
+------------+-----------+
             |
             v
+------------------------+
| 生成检索输入            |
| - 查询文本              |
| - 检索条件              |
| - 优先证据方向          |
+------------------------+
```

---

## 4.3 混合召回

当前项目中的 RAG 不是单一路径召回，而是混合召回。

核心思路是同时利用：

- 语义相似能力
- 关键词匹配能力

然后将两类结果进行合并与排序，形成更稳定的召回结果。

这样做的作用是：

- 避免只依赖语义召回导致遗漏关键字命中
- 避免只依赖关键词召回导致遗漏语义近似内容
- 提高检索结果的覆盖度与稳定性

### 4.3.1 混合召回流程图

```text
+------------------------+
| 查询整理结果            |
+------------+-----------+
             |
             v
+------------------------+      +------------------------+
| 语义召回                |      | 关键词召回              |
| - 相似语义匹配          |      | - 关键词规则匹配        |
| - 相关内容扩展          |      | - 精确短语命中          |
+------------+-----------+      +------------+-----------+
             |                               |
             +---------------+---------------+
                             |
                             v
                  +------------------------+
                  | 召回结果合并与粗排序    |
                  | - 覆盖度                |
                  | - 相关性                |
                  +------------+-----------+
                               |
                               v
                  +------------------------+
                  | 输出候选知识集          |
                  +------------------------+
```

## 4.4 结果过滤与证据组织

召回得到的内容不会直接原样送入模型。

系统会继续处理这些结果，包括：

- 过滤噪声
- 去除不合格内容
- 保留与任务更相关的片段
- 将长内容整理成更适合注入上下文的证据材料
- 保留证据结构，方便后续推理使用

这一阶段的目标，是把“检索结果”转成“可用于推理和生成的证据材料”。

## 4.5 记忆命中与结果合流

在当前项目里，知识检索结果不会完全独立于记忆系统。

系统还会在适当时机补充：

- 会话记忆命中
- 历史任务摘要
- 与当前任务相关的历史事实

然后把这些结果与知识检索结果一起组织成统一上下文候选。

也就是说，RAG 在当前项目中并不是只有知识库检索，还会与记忆结果协同工作。

### 4.5.1 记忆合流视图

```text

| - 证据块                |      | - 既有事实              |
+------------+-----------+      +------------+-----------+
             |                               |
             +---------------+---------------+
                             |
                             v
                  +------------------------+
                  | 统一上下文候选集        |
                  | - 当前知识证据          |
                  | - 会话连续性信息        |
                  +------------------------+
```

## 4.6 上下文治理与注入

RAG 的最终目标不是“找到内容”，而是“把合适的内容送进模型上下文”。

因此在检索完成后，系统还会进行上下文治理，处理：

- 哪些检索结果真正值得进入当前轮
- 哪些内容应该裁剪
- 哪些内容应该降级
- 检索结果与历史、工具结果之间如何平衡
- 在上下文预算内保留哪些内容

经过治理后的结果，才会真正进入后续推理或结果生成阶段。

### 4.6.1 RAG 注入视图

```text
检索结果 + 记忆结果 + 当前任务信息 + 工具结果
                    |
                    v
       +-------------------------------+
       |         上下文治理层           |
       | 预算 / 裁剪 / 排序 / 合并 / 装配 |
       +---------------+---------------+
                       |
                       v
       +-------------------------------+
       |      模型实际可见上下文         |
       +-------------------------------+
```

## 5. RAG 在系统中的作用

在当前项目里，RAG 主要服务于以下几个方向：

### 5.1 服务规划

规划阶段需要知道当前任务是否缺少背景知识，以及后续是否需要知识支持。

### 5.2 服务推理

推理阶段需要证据材料来支撑结果组织与内容生成。

### 5.3 服务工程判断与结果生成

在工程交付、规范解释、方案比较或结果说明阶段，检索结果也可以作为背景知识、规则依据和判断证据被消费。

### 5.4 服务记忆与连续性

检索链路和记忆链路共同工作，使系统在新一轮任务中不仅能看当前输入，也能带上必要的历史与知识支撑。

Skills 在当前项目中的目标，是把不同场景下的系统行为组织成稳定的策略包。

Skills 关注的不是“系统能不能做”，而是“在这个场景下应该怎么做”。

## 7. Skills 流程详细说明

## 7.1 任务识别与场景判断

系统在接到任务后，需要识别当前任务更适合哪种场景。

例如，一个任务可能偏向：

- 通用问答
- 工程交付
- 审核评估
- 持续推进型任务
- 其他特定能力包

在这个阶段，系统会把任务与合适的场景能力联系起来。

---

## 7.2 选择或附加 Skill

当系统确认当前任务处于某个场景时，会选择对应的 Skill，或者把某个 Skill 附加到当前任务上。

这一步的目标是让后续规划和执行不再只依赖通用逻辑，而是带着场景化约束前进。

### 7.2.1 Skill 选择视图

+------------+-----------+
             |
             v
+------------------------+
| 选择默认 Skill          |

+------------------------+

## 7.3 解析 Skill 策略内容

一个 Skill 在系统中的作用，不只是给模型一段额外提示，而是提供一整组场景化约束。

常见约束包括：

- 允许使用哪些工具
- 不允许使用哪些工具
- 规划阶段应偏向什么行为
- 推理阶段应偏向什么表达或判断方式
- 输出应满足什么结构契约
- 当前场景的风险边界是什么

这一步会把 Skill 解析成运行时真正可消费的策略结果。

---

## 7.4 注入规划与执行流程

Skill 生效之后，不会停留在静态定义层，而是会真正参与后续执行。

它会影响的部分包括：

- 规划阶段的计划生成
- 工具选择边界
- 推理阶段的行为偏置
- 输出阶段的结构要求
- 风险控制与校验方式

因此，Skill 是一种“运行时场景策略注入”。

## 7.5 影响工具选择与动作边界

Skill 不直接替代工具，但会决定在某个场景下：

- 哪些工具是当前可用的
- 哪些工具必须被限制
- 哪些能力应优先使用
- 哪些输出方式应优先采用

因此，Skill 对执行动作的影响非常直接。

它实际上决定了系统在该场景中的“能力边界与行为方式”。

## 7.6 输出契约与结果收敛

Skill 还会影响系统最终结果的形式。

它可以约束：

- 输出是否结构化
- 输出的重点是什么
- 场景中哪些内容必须体现
- 场景中哪些内容应避免出现

这使得系统在不同场景下能形成相对稳定的结果风格。

---

## 8. Skills 在系统中的作用

在当前项目中，Skills 的主要作用有四类。

### 8.1 统一场景行为

让系统面对同类任务时，不必每次都从零决定行为模式。

### 8.2 约束能力边界

让不同任务场景下的工具使用、规划方式和输出方式保持稳定。

### 8.3 提高执行一致性

使系统在多次执行同类任务时保持类似的行为风格与策略边界。

### 8.4 让平台具备能力包装能力

不仅能提供底层能力，还能把底层能力包装成可面向不同场景复用的执行能力包。

## 9. RAG 与 Skills 的协同流程

RAG 与 Skills 并不是两条互斥链路，而是会在统一运行时中共同作用。

### 9.1 协同逻辑

- Skill 决定当前场景下系统怎么做
- RAG 决定当前场景下系统拿什么知识来做

## 10. 总结

### 10.1 RAG 的本质

RAG 是当前项目中的知识支撑流程。它负责在任务需要知识时，完成检索、证据组织、记忆合流和上下文注入。

### 10.2 Skills 的本质

Skills 是当前项目中的场景策略流程。它负责在不同任务场景下，为系统提供行为边界、能力约束、规划偏置和输出契约。

### 10.3 二者关系

- RAG 提供知识材料
- Skills 提供场景策略
- 二者共同服务统一 Agent Runtime

### 10.4 一句话总结

当前项目中的 RAG 负责“给系统补知识与证据”，Skills 负责“让系统在特定场景下按一致策略做事”，二者共同构成统一运行时中的关键流程。
