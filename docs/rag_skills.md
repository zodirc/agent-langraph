# RAG 与 Skills 流程说明

## 1. 文档目标

这份文档专门说明当前项目中的两条核心流程：

- RAG 流程
- Skills 流程

文档只描述当前项目中的实际架构与执行方式，不讨论问题、不提出假设、不贴实现文件路径，也不贴代码路径。

目标是从系统流程角度，把这两个能力说明清楚。

---

## 2. 整体关系

在当前项目中，RAG 与 Skills 并不是两套彼此孤立的系统，而是统一运行时中的两个重要部分：

- **RAG** 负责为任务提供知识与证据支撑
- **Skills** 负责为任务提供场景策略、行为约束与能力边界

它们都服务于统一 Agent Runtime，但职责不同。

### 2.1 两者在系统中的位置

- RAG 更接近“知识补给与证据组织”
- Skills 更接近“场景约束与策略驱动”

二者都会影响规划、工具选择、上下文组织和最终输出结果。

### 2.2 两者协同关系

- Skills 决定系统在某个场景下如何做事
- RAG 决定系统在需要知识支撑时拿什么材料做事

所以它们的关系不是替代，而是协同。

## 3. RAG 流程总览

RAG 在当前项目中的目标，是为规划、推理、工程判断与结果生成提供知识支撑与证据材料。

它不是整个系统的总代称，而是统一运行时中的一个关键子流程。

## 4. RAG 流程详细说明

## 4.1 检索触发

RAG 流程并不是每次输入都强制执行，而是由前面的规划阶段决定是否需要知识支持。

也就是说，系统会先判断：

- 当前任务是否依赖外部知识
- 当前任务是否需要事实性支撑
- 当前任务是否需要背景材料
- 当前任务是否需要补足历史记忆之外的信息

当系统判断需要知识支撑时，才会进入检索链路。

**文稿写作例外**：`manuscript_mode` 且 `writing_intent.enabled` 时，规划阶段默认 `skip_retrieval=False`，检索域含 `{writing, common}`，已上传会话素材走 `source` 域（与风格规范一并注入写作 payload，不依赖模型每回合自行 emit `retrieve`）。首轮 `kickoff_novel` 薄路径固定 `read_artifact(素材卡)` → `write_artifact(大纲)`，素材卡（Story Bible）由上传蒸馏后确定性注入生成 prompt。其余模式仍由规划 actions 与 `skip_retrieval` 决定。

---

## 4.2 检索意图与查询整理

在进入真正的召回之前，系统会先把当前任务转换为更适合检索的查询形式。

这一步的目标是让系统不要直接拿原始用户话术去搜，而是先整理出：

- 当前检索的目的
- 更适合检索的查询文本
- 必要的检索限制条件
- 与当前任务相关的上下文信息

**默认**会先做轻量整理（含正则代词消解等零成本改写）。**可选开关**（默认关）可在低召回或准入全过滤时启用 **LLM 查询改写**，并扩展 **multi-query** 子查询合并召回，以提高复杂问句与改写类查询的命中率。

这一阶段的输出，是后续召回所依赖的检索输入对象。

```text
+------------------------+
| 原始用户目标            |
+------------+-----------+

+------------------------+
| 任务语义抽取            |

| - 约束                  |
| - 目标类型              |
+------------+-----------+

             v
+------------------------+
| 检索目的判断            |

+------------------------+
```

## 4.3 混合召回

当前项目中的 RAG 不是单一路径召回，而是混合召回。

核心思路是同时利用：

- 语义相似能力
- 关键词匹配能力

然后将两类结果进行合并与排序，形成更稳定的召回结果。

**语义路径**依赖向量索引；**关键词路径**默认使用 BM25（含 CJK bigram）。在 SQLite 存储且开启 **FTS 开关**时，关键词路径可走 **FTS5 倒排索引**，避免大语料全表扫描。两路结果经 **RRF** 合并后进入重排与 relevance 准入。

这样做的作用是：

- 避免只依赖语义召回导致遗漏关键字命中
- 避免只依赖关键词召回导致遗漏语义近似内容
- 提高检索结果的覆盖度与稳定性

### 4.3.1 混合召回流程图

```text
+------------------------+
| 查询整理结果            |
+------------+-----------+
             |
             v
+------------------------+      +------------------------+
| 语义召回                |      | 关键词召回              |
| - 相似语义匹配          |      | - 关键词规则匹配        |
| - 相关内容扩展          |      | - 精确短语命中          |
+------------+-----------+      +------------+-----------+
             |                               |
             +---------------+---------------+
                             |
                             v
                  +------------------------+
                  | 召回结果合并与粗排序    |
                  | - 覆盖度                |
                  | - 相关性                |
                  +------------+-----------+
                               |
                               v
                  +------------------------+
                  | 输出候选知识集          |
                  +------------------------+
```

## 4.4 结果过滤与证据组织

召回得到的内容不会直接原样送入模型。

系统会继续处理这些结果，包括：

- 过滤噪声
- 去除不合格内容
- 保留与任务更相关的片段
- 将长内容整理成更适合注入上下文的证据材料
- 保留证据结构，方便后续推理使用

上述步骤在**证据管线**中完成：混合召回 → **重排**（默认词法，可选 cross-encoder / 第三方 rerank）→ **relevance 准入**（按 purpose 设最小分与 top-k）→ 去重、来源多样性、**冲突检测**、证据 token 预算裁剪与失败归因。

**证据 token 预算**默认独立配置；开启 **budget_link_context** 后，与上下文治理中 `retrieved_knowledge` 桶 cap 联动，减少「检索层保留、上下文层再砍」的双层损耗。组装 envelope 时可记录 **证据保真率**（高分证据进入 prompt 的比例）供观测与回归。

这一阶段的目标，是把“检索结果”转成“可用于推理和生成的证据材料”。

```text
+------------------------+

+------------+-----------+
             |

| 片段截取与结构整理      |
| - 保留关键段落          |
| - 压缩长文本            |

+------------+-----------+
             |

+------------------------+

| - 证据块                |

+------------------------+
```

## 4.5 记忆命中与结果合流

在当前项目里，知识检索结果不会完全独立于记忆系统。

系统还会在适当时机补充：

- 会话记忆命中
- 历史任务摘要
- 与当前任务相关的历史事实

然后把这些结果与知识检索结果一起组织成统一上下文候选。

也就是说，RAG 在当前项目中并不是只有知识库检索，还会与记忆结果协同工作。

## 4.6 上下文治理与注入

RAG 的最终目标不是“找到内容”，而是“把合适的内容送进模型上下文”。

因此在检索完成后，系统还会进行上下文治理，处理：

- 哪些检索结果真正值得进入当前轮
- 哪些内容应该裁剪
- 哪些内容应该降级
- 检索结果与历史、工具结果之间如何平衡
- 在上下文预算内保留哪些内容

治理经**统一 prompt 上下文网关**按当前 **purpose** 执行：收集多源材料 → 解析 **prompt token 预算** → 分桶 cap → 压缩 → 丢弃 → 全局降级 → 输出 **envelope**。

### 4.6.1 预算模式

| 配置项 | 窗口自适应**开**时是否决定「这次 prompt 塞多少」 |
|---|---|
| `window_adaptive_budget` + `window_utilization` + floor/ceiling | **是** |
| purpose 策略 cap（如 reasoning ~32K） | **否**（仅作桶 cap 缩放比例参考） |
| `default_token_budget`（64800） | **否**（除非请求显式传 `token_budget`） |

| 模式 | 单次 prompt 预算 |
|---|---|
| 窗口自适应关（仓库默认） | `min(purpose 策略 cap, 任务剩余)`，长窗口利用率低 |
| 窗口自适应开（部署可灰度） | `clamp(模型窗口 × 占用率 − 已用 − 输出预留, 下限, 上限)`；桶 cap 可随 budget 等比放大 |

**64800 仍用于**（与 adaptive 并行）：会话占用条分母、七桶初始化 `total_budget`、API 可选 `token_budget` 上限、预算解析异常时的回退。未显式传任务 token 上限时，adaptive 算出的 budget **不受 64800 封顶**，只受 `prompt_budget_ceiling`（默认 160000）与窗口公式约束。

**模型窗口**解析顺序：catalog → 模型名推断 → `model.context_window` → 默认 128000。配置值须匹配模型**真实**能力，不宜为不支持的模型虚配 200K。

**数值示例**（200K 窗口、占用率 0.6、reasoning、输出预留约 8192）：`budget ≈ 111808`（非整窗 200K 全给 prompt）。

### 4.6.2 压缩与可观测

超桶 cap 时优先结构化裁剪；知识/工具类证据可走**抽取式句子保留**；可选语义压缩（默认关）。压缩产出 **compression_receipts**（如 dropped_entities、kept_anchors）写入 trace，便于审计「截掉了什么」。

### 4.6.3 RAG 注入视图

```text
检索结果 + 记忆结果 + 当前任务信息 + 工具结果
                    |
                    v
       +-------------------------------+
       |         上下文治理层           |
       | 预算解析 / 分桶 / 压缩 / 装配  |
       | + 压缩回执 / 证据保真率 trace  |
       +---------------+---------------+
                       |
                       v
       +-------------------------------+
       |      模型实际可见上下文         |
       +-------------------------------+
```

## 5. RAG 在系统中的作用

在当前项目里，RAG 主要服务于以下几个方向：

### 5.1 服务规划

规划阶段需要知道当前任务是否缺少背景知识，以及后续是否需要知识支持。

### 5.2 服务推理

推理阶段需要证据材料来支撑结果组织与内容生成。

**文稿写作消费**：`domain=writing` 的召回片段经 `writing_context` 组装为 `writing_guidelines_excerpt`，`domain=source` 的会话素材组装为 `session_source_excerpt`，随写作 purpose 的 governed payload 注入生成阶段（与 `continuation_rules` 并列）；写回工具结果可附带 `applied_guidelines` / `applied_sources`（doc_id 列表）供回合摘要与归因。

**素材卡与 RAG 的分工**（硬约束 vs 补充检索）：

| 通道 | 时机 | 作用 |
|---|---|---|
| **素材卡（Story Bible）** | 上传 `domain=source` 后后台蒸馏为 `素材卡.md` | 改编要求等硬约束**确定性全文注入** prompt，不依赖向量命中 |
| **`source` 域 RAG** | 写作回合 `skip_retrieval=False` 时 | 风格片段、会话素材补充；超长原文（>5 万字）时按大纲 query 召回细节 |
| **薄路径读文件** | `kickoff_novel` 等算子 | playbook 显式 `read_artifact(素材卡)`，与上述注入叠加，保证规划阶段已知素材结构 |

检索 0 命中但库内仍有 `source` 文档时记 `source_recall_miss`；用户可见回复尾部「本轮素材使用：素材卡 N 字 + 原文检索 M 段」。项目契约与算子细则见 `docs/arch.md` §5.2。

**output_guard 与写作轮**：忠实度闸门按回合契约与 `answer_mode` 判定，而非仅凭召回域或回复措辞。写作澄清/追问/状态回合（无落盘、非严格事实问答）不跑词面重合硬 REJECT；混合 `writing+source` 召回不再误杀「请补充素材」类回复。事实问答与伪造引用仍硬拦。流程侧见 `docs/arch.md` §4.4、§5.2。

离线可用 `tests/eval/run_writing_rag_ab_eval.py` 对开/关 RAG 做规范遵循度 A/B，阈值门见 `tests/eval/eval_thresholds.py` 中 `check_writing_compliance_thresholds`。

### 5.3 服务工程判断与结果生成

在工程交付、规范解释、方案比较或结果说明阶段，检索结果也可以作为背景知识、规则依据和判断证据被消费。

### 5.4 服务记忆与连续性

检索链路和记忆链路共同工作，使系统在新一轮任务中不仅能看当前输入，也能带上必要的历史与知识支撑。

### 5.5 可选检索与治理增强（配置开关）

以下能力已落地，**默认关或保持保守默认**，可按需灰度，不改变未开启时的运行时行为：

| 能力 | 默认 | 说明 |
|---|---|---|
| FTS5 关键词索引 | 关 | SQLite 下加速 BM25/关键词召回 |
| LLM 查询改写 + multi-query | 关 | 低召回重试时扩展查询 |
| cross_encoder / cohere 重排 | lexical | 提升排序质量，成本更高 |
| budget_link_context | 关 | 证据预算与上下文桶 cap 联动 |
| window_adaptive_budget | 关（Docker 可开） | prompt 预算随模型窗口缩放 |
| semantic 语义压缩 | 关 | 超 cap 时 LLM 压缩（extractive 默认开） |

**灰度建议**：Compose 可在 `config.docker.yaml` 开 `window_adaptive_budget`；生产先观察 trace 中 `token_budget_total`、延迟与成本，再改仓库默认。`budget_link_context`、`fts_enabled` 等与窗口自适应独立，按需逐项开启。系统总览与 CI 回归门见 `docs/arch.md` §2.6、§4.6。

## 6. Skills 流程总览

Skills 在当前项目中的目标，是把不同场景下的系统行为组织成**可声明、可解析、可注入**的策略包。与 `mode_contracts`（按 `qa_mode` / `manuscript_mode` / `engineering_mode` 的全局偏置）互补：Skill 由任务 API **显式挂载**（`skill_id`），在单次任务内叠加工具边界与 prompt overlay。

Skills 关注的不是“系统能不能做”，而是“**在这个已选 Skill 下应该怎么做**”。

### 6.0 与模式契约（mode contract）的分工

| 机制 | 绑定粒度 | 典型内容 |
|---|---|---|
| **mode contract** | 会话/任务模式（`target_mode`） | 默认工具集、步数偏置、工程隔离 |
| **Skill** | 单次任务可选（`skill_id`） | `allowed_tools` / overlay / `output_contract` / 执行模式提示 |

二者可同时生效：模式决定大方向，Skill 在任务创建时进一步收窄或偏置规划/推理行为。

### 6.1 Skills 总体流程图

## 7. Skills 流程详细说明

## 7.0 配置与定义来源

- **配置开关**：`config.yaml` → `skill.enabled`、`skill.runtime_policy_enabled`（默认均为 true）
- **内置定义目录**：`config/skills/*.yaml`（如 `qa_general`、`chapter_writer`、`novel_outline`、`code_review` 等）
- **可选扩展**：`config/skill_packages/`（`packages_enabled`）、租户级 `data/skills/`

每个 Skill YAML 定义至少包含：`skill_id`、`allowed_tools` / `blocked_tools`、`planning_overlay`、`reasoning_overlay`、可选 `reflection_overlay` 与 `output_contract`。

## 7.1 任务挂载与解析

用户在创建任务时可通过 API 传入 `skill_id` 与 `skill_params`。图执行前完成两阶段解析：

1. **API 阶段**（`attach_skill_to_payload`）：校验 skill 存在、状态为 published、角色/租户可见 → 写入 `input_payload._skill_policy` 与 `_skill_snapshot`
2. **图启动阶段**（`apply_skill_from_payload`）：剥离内部键，执行 `pre_task` hook，将 **`skill_runtime_policy`** 提升到 `AgentState`

`skill_runtime_policy` 核心字段：

| 字段 | 作用 |
|---|---|
| `resolved_tool_allowlist` / `resolved_tool_blocklist` | 与 domain pack 工具集求交，约束规划与 `validate_tool_selection` |
| `resolved_planning_overlay` | 注入规划 system prompt（`[Skill overlay]` 段） |
| `resolved_reasoning_overlay` | 注入推理 system prompt |
| `resolved_reflection_overlay` | 注入反思 prompt（若走 reflection LLM） |
| `resolved_output_contract` | 输出结构约束（供 output_guard 等消费） |
| `resolved_action_weights` | 可选 action 偏置权重 |

Overlay 文本支持 `skill_params` 模板渲染（如 goal 占位）。

## 7.2 任务识别与场景判断

系统在接到任务后，除 **pre_planning 的模式解析**（`target_mode`、route_audit、intent_observation）外，若 payload 含 `skill_id`，则 Skill 策略与模式契约 **并行生效**。

Skill **不替代** 事件分类或 `target_mode` 推断；它是在模式确定（或显式指定）之后，对单次任务叠加的策略层。

例如，一个任务可能偏向：

- 通用问答（`qa_mode` + `skill_id=qa_general`）
- 长文章节（`manuscript_mode` + `skill_id=chapter_writer`）
- 工程交付（`engineering_mode` + `skill_id=code_review`）

## 7.3 选择或附加 Skill

当 API 请求携带 `skill_id` 时，系统在图执行前完成解析并挂载；未携带时 Skill 层不生效，仅依赖 mode contract 与默认 domain overlay。

若 Skill 定义含 `preferred_execution_mode` 或 `base_domain`，且 payload 未显式覆盖，解析结果可写入 payload 的 `execution_mode` / `domain` 提示（不强制覆盖 `target_mode`）。

## 7.4 解析 Skill 策略内容

一个 Skill 在系统中的作用，不只是给模型一段额外提示，而是提供一整组场景化约束。

常见约束包括：

- 允许使用哪些工具
- 不允许使用哪些工具
- 规划阶段应偏向什么行为
- 推理阶段应偏向什么表达或判断方式
- 输出应满足什么结构契约
- 当前场景的风险边界是什么

这一步会把 Skill 解析成运行时真正可消费的策略结果。

## 7.5 注入规划与执行流程

Skill 生效后参与以下环节（均读取 `state.skill_runtime_policy`）：

| 阶段 | 注入方式 |
|---|---|
| **规划** | `build_planning_system_prompt` 追加 `resolved_planning_overlay`；`merge_domain_pack_tools_with_skill` 收窄 `runtime_capabilities` 工具集 |
| **工具执行** | `validate_tool_selection` 与 allowlist/blocklist 对齐 |
| **推理** | reasoning system prompt 追加 `resolved_reasoning_overlay` |
| **反思** | 若走 reflection LLM，追加 `resolved_reflection_overlay`；写作算子结构化反思时 overlay 仍可用于边界提示 |
| **任务结束** | `record_skill_task_finished` 写入 skill 指标 |

trusted plugin hooks（`HOOK_TYPE_PLANNING`、`HOOK_TYPE_TOOL_FILTER`）可在解析阶段进一步 patch policy。

## 7.6 影响工具选择与动作边界

Skill 不直接替代工具，但会决定在某个场景下：

- 哪些工具是当前可用的
- 哪些工具必须被限制
- 哪些能力应优先使用
- 哪些输出方式应优先采用

因此，Skill 对执行动作的影响非常直接。

它实际上决定了系统在该场景中的“能力边界与行为方式”。

## 7.7 输出契约与结果收敛

Skill 还会影响系统最终结果的形式。

它可以约束：

- 输出是否结构化
- 输出的重点是什么
- 场景中哪些内容必须体现
- 场景中哪些内容应避免出现

这使得系统在不同场景下能形成相对稳定的结果风格。

## 8. Skills 在系统中的作用

在当前项目中，Skills 的主要作用有四类。

### 8.1 统一场景行为

让系统面对同类任务时，不必每次都从零决定行为模式。

### 8.2 约束能力边界

让不同任务场景下的工具使用、规划方式和输出方式保持稳定。

### 8.3 提高执行一致性

使系统在多次执行同类任务时保持类似的行为风格与策略边界。

### 8.4 让平台具备能力包装能力

不仅能提供底层能力，还能把底层能力包装成可面向不同场景复用的执行能力包。

## 10. 总结

### 10.1 RAG 的本质

RAG 是当前项目中的知识支撑流程。它负责在任务需要知识时，完成查询整理（含可选 LLM 改写）、混合召回（含可选 FTS）、证据管线、记忆合流，并在上下文治理层完成预算解析、分桶压缩与注入；可选开关控制重排升级、预算联动与窗口自适应，默认行为保持保守。

### 10.2 Skills 的本质

Skills 是当前项目中的**可选任务级策略包**：YAML 定义 → API 挂载 → `skill_runtime_policy` → 工具 allowlist 与 planning/reasoning/reflection overlay 注入。与 `mode_contracts` 的全局模式偏置叠加，而非替代事件分类或 `target_mode` 解析。

### 10.3 二者关系

- RAG 提供知识材料
- Skills 提供场景策略
- 二者共同服务统一 Agent Runtime

### 10.4 一句话总结

当前项目中的 RAG 负责「给系统补知识与证据，并在治理层按 purpose 与预算装配进模型上下文」；Skills 负责「让系统在特定场景下按一致策略做事」。二者共同构成统一运行时中的关键流程。
